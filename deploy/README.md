# Серверный комплект закрытого теста «Ось коммуникации»

Это комплект для отдельного тестового VPS. Реальные Docker/PostgreSQL, права systemd, публичный домен и два телефона ещё требуют приёмки. Он не снимает Development-only guard. Проверенная Release-сборка — серверный API, не Android APK и не готовый Docker image.

## Установка сервисов

1. Разместить единственный deploy-checkout в `/opt/os-communications`. До изменений сохранить данные уже работающего сервера; не останавливать другие сайты. Нужны Docker Compose v2 с `up --wait`, Nginx, Python 3.10+ и age. Точные пути бинарников в unit проверить на VPS.
2. Создать `.env` только при новой установке через `scripts/init-dev.py`. Существующий файл сохранить, права 0600. `AllowedHosts` установить в реальный домен. Fake SMS оставить до отдельной проверки. Операторские пути включать только при необходимости и отдельно ограничивать IP.
3. Подготовить HTTPS по `docs/CLOSED_HTTPS.md`. Для пользователя `os-closed-https` дать проход по каталогам и чтение config/certificate/key через контролируемую группу, конфигурации оставить недоступными для записи этому пользователю. Запись — только в `runtime/`. Генератор создаёт всё приватным для своего владельца; сам по себе он доступ сервисному пользователю не выдаёт. Не использовать `chmod -R 777`.
4. Проверить шаблоны в `deploy/systemd/`, убрать суффикс `.example` при установке выбранных файлов в `/etc/systemd/system/`. Compose unit запускается администратором Docker и использует `compose.yaml` вместе с `deploy/compose.runtime.yaml`: контейнеры возвращаются после аварии/перезагрузки, ручная остановка сохраняется. Привилегии Docker фактически административные; это не непривилегированный пользователь API. Сам API внутри образа остаётся под `$APP_UID`.
5. HTTPS unit запускает отдельный foreground Nginx с единственной capability для порта 443. Он не управляет общим nginx.service и не поддерживает общий reload. Проверить отсутствие конфликта 443, закрытый firewall, сертификат/цепочку, API peer после Docker NAT и точный `Auth:TrustedProxies`.
6. После проверки путей/прав выполнить `systemd-analyze verify` на установленных unit, затем `systemctl daemon-reload`. Запускать сначала `os-communications-compose.service`, проверить `/health/ready` с разрешённым Host через loopback, затем выделенный HTTPS unit. `compose up --wait` без API healthcheck подтверждает запуск контейнера, а не готовность API/миграций. Только после ручной приёмки включить unit на автозапуск.

Нельзя применять `docker compose down -v`, prune volumes или пересоздавать `.env` ради ошибки запуска. Публичны только разрешённые HTTPS/SSH, база и API остаются закрыты. Шаблоны здесь прошли только offline syntax verification с заменой отсутствующих локальных бинарников/внешних unit; запуск и boot/restart на VPS не проверены.

## Release-артефакт

Опубликованный архив содержит результат `dotnet publish` и контрольные суммы, без рабочих секретов. Это framework-dependent сборка: нужен совместимый ASP.NET Core 10 runtime и настроенная PostgreSQL/секреты. Исходный Dockerfile сам собирает API из checkout и создаёт каталог Data Protection с правильным владельцем; его путь остаётся основным способом сборки образа. Готовый контейнер в текущей среде не собирался — Docker отсутствует. Не подменять образ голым aspnet image с непроверенными правами на новый volume.

## Зашифрованные резервные копии

`server-backup.py` предназначен для этого одного Compose deployment: сервисы `api`/`db`, БД и пользователь `messenger`, Data Protection `/data/protection`. Другие экземпляры API и сторонние писатели не покрываются согласованием снимка. Полные рабочие сценарии Docker/pg_dump и восстановление в PostgreSQL здесь ещё не выполнены.

Ключ создать **на отдельном защищённом компьютере**:

```bash
age-keygen -o backup.identity
age-keygen -y backup.identity
```

Первый файл — секрет для восстановления, хранить офлайн с правами 0600 и отдельной резервной копией. На сервер передаётся только проверенный публичный recipient `age1…`. Не использовать SSH-ключ приложения или Android Signal keys. Для автозапуска создать приватный `/etc/os-communications/backup.env` с единственной несекретной настройкой `OS_BACKUP_RECIPIENT=полный_публичный_age_recipient`; установить age и приватный каталог `/var/backups/os-communications` 0700.

Ручной запуск (полностью заменить PUBLIC_AGE_RECIPIENT, placeholder не сработает):

```bash
python3 scripts/server-backup.py backup \
  --root /opt/os-communications \
  --recipient PUBLIC_AGE_RECIPIENT \
  --destination /var/backups/os-communications \
  --quiesce-api
```

**Операция кратковременно останавливает API**, если он работал. `--quiesce-api` — явное подтверждение этого поведения. После попытки API возвращается в прежнее состояние; уже остановленный API не запускается. При ошибке запуска API команда завершится ошибкой, администратор должен немедленно проверить сервис. Согласование одной БД и keyring требует остановки всех других писателей, если они есть. Lock запрещает параллельные запуски из этого checkout.

В копии: custom pg_dump, `.env`, все обычные плоские файлы Data Protection и метаданные. Они зашифрованы age; приватного ключа восстановления на сервере не требуется. `.env` и Data Protection временно читаются/копируются в приватный staging 0700, затем удаляются; гарантии secure erase на SSD нет. Dump сразу поступает в шифрование без открытого файла. Закрытые файлы серверных настроек и keyring считаются чувствительными даже при отсутствии plaintext сообщений.

Готовая папка публикуется только после успешных dump/encryption; содержит `database.dump.age`, `server-state.tar.age`, manifest с SHA256 ciphertext и связанными encrypted metadata. Внешние TLS keys, ключ age и настройки самого VPS в этот формат не входят — их сохранять отдельно. Это логический снимок одной БД, без ролей/кластерных настроек и без PITR/WAL. Автоматического удаления старых копий или отправки на внешнее хранилище пока нет: объём диска контролировать, копии переносить во второе защищённое место.

Timer-шаблон задаёт ежедневное окно 03:30 по Москве с задержкой до 10 минут. Включать timer только после ручного успешного backup и теста восстановления; наличие unit не означает, что расписание уже установлено.

## Проверка копии и восстановление

На защищённом компьютере с офлайн-ключом и age, в **новый** приватный каталог:

```bash
python3 scripts/server-backup.py verify \
  --backup /secure/backup-SELECTED_ID \
  --identity /secure/backup.identity \
  --output /secure/verified-SELECTED_ID
```

Проверка сверяет hashes, полностью завершает authenticated decryption, проверяет связь DB/state и безопасно извлекает файлы. Она **не подключается к БД и не восстанавливает живой сервер**. При ошибке новый plaintext output не публикуется. В нём после успеха находятся открытый dump и серверные секреты — не загружать каталог в GitHub/чат, не выдавать права другим и удалить после контролируемого восстановления.

age защищает целостность ciphertext и доступ получателя, но не подтверждает автора: любой знающий публичный recipient может зашифровать новый файл. Проверять происхождение копии и использовать только свои доверенные backups. PostgreSQL dump при восстановлении может выполнять SQL; не восстанавливать неизвестный dump.

Следующая обязательная приёмка: восстановить `database.dump` через PostgreSQL 18 `pg_restore --exit-on-error --single-transaction --no-owner --no-acl` в **отдельный пустой тестовый экземпляр/volume**, затем сопоставить таблицы/счётчики и проверить API с восстановленными `.env`/Data Protection. Не использовать рабочую БД или рабочий volume, не переносить секреты в действующий checkout автоматически. Для реального аварийного переключения нужен отдельный план отключения старого экземпляра и отзыва/защиты его секретов.

Официальные основания: [pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html), [age](https://github.com/FiloSottile/age). Тесты ниже проверяют настоящее age, но Docker и pg_dump заменены транспортными fixtures — это не проверка восстановления PostgreSQL.

```bash
python3 -m unittest discover -s scripts/tests -p test_server_backup.py -v
```
