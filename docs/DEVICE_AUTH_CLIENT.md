# Ось коммуникации: подтверждение устройства и клиентская авторизация

Клиентский код объединяет PR #3 и сетевую основу Claude PR #4. Бренд — «Ось коммуникации», протокольные идентификаторы сохраняются.

## Реализованные компоненты

- DeviceProofPayload.java — строгие канонические activate/refresh байты; Kotlin DeviceProof использует тот же построитель.
- DeviceAuthKey — отдельный неэкспортируемый P-256 ключ Android Keystore, реализующий DeviceSigner. Приватный Signal identity для подписи не используется.
- AuthApi — pinned HTTPS, ограниченный ответ, машинные ошибки, отдельные анонимные auth-запросы без Authorization.
- Login — сохранённый до отправки requestId, SMS и PIN шаги, проверка сессии перед сохранением. Номер хранится в зашифрованном профиле, строковые представления DTO скрывают его и секреты.
- UserSession / VaultAuthStore — refresh в одном экземпляре, durable journal и бюджет идентичного повтора, атомарное сохранение до использования access. Access остаётся в памяти, refresh — в SQLCipher.
- PinnedApi — провайдер access с одним повтором после 401; старый операторский режим сохранён.
- Текстовый бренд в четырёх языках; проект внешнего API в OS_INTEGRATION_V1.md и OS_INTEGRATION.openapi.yaml. Основная система в эту работу не входит.

## Следующее подключение в Android

1. Создавать новый профиль SQLCipher/Signal и новый deviceId на каждую активацию; существующий профиль нельзя перепривязать или тихо очистить.
2. Сохранять стадию создания ключей/профиля до сети. Создание auth key не перезаписывает прежний alias, потеря ключа завершает вход закрытым отказом.
3. Владеть одним UserSession на активный профиль на уровне приложения: отдельные ViewModel не создают конкурирующие refresh-контроллеры.
4. Подключить экраны номера, SMS-кода и PIN, таймеры, ошибки четырёх языков, настройку PIN и logout. Секреты не сохранять в SavedState/Intent/clipboard.
5. После активации проверить `/me` и собственные Signal keys, неизменяемо bind профиль, публиковать prekeys, затем активировать Delivery. Только после этого показывать сетевой чат.
6. Для REFRESH_RECOVERY_EXPIRED / REFRESH_RETRY_EXHAUSTED / REFRESH_OUTCOME_UNKNOWN останавливать сеть, сохранять прежнюю историю и outbox, предлагать новый вход в новом профиле. Не брать новый challenge с возможно потреблённым refresh.
7. Проверить аппаратный Keystore и сценарии на Android, живой API и два физических телефона. Текущая UI-сборка всё ещё использует отдельную операторскую сессию; пользовательский вход не подключён.
