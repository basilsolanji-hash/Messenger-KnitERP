# Авторизация v1: модель угроз, состояния и решения

Ветка `claude/auth-v1`, 22 октября 2026 года. Серверная часть SMS-входа, PIN, подтверждения владения устройством и refresh rotation. Android-интерфейс входа ещё не подключён. Контракт API описан в [API_AUTH.md](API_AUTH.md), поток клиента — в [ANDROID_AUTH.md](ANDROID_AUTH.md).

**Предохранитель `Development` не снят.** Появление этих endpoint не разрешает публичный запуск. Снятие — отдельное решение после проверки Android, эксплуатации, юридических условий и независимой проверки безопасности.

## Что защищаем и от кого

| Актив | Угроза | Мера |
| --- | --- | --- |
| Аккаунт по номеру | Перебор SMS-кода | 6 цифр, 5 попыток на challenge, TTL 5 мин, отправка не чаще 1 раза в 60 с, 3 за 15 мин и 10 в сутки на номер. Ожидаемая вероятность угадывания ≤ 50 / 10⁶ в сутки на номер |
| Аккаунт с PIN | Захват номера (SIM swap, перехват SMS) | Одной SMS недостаточно. PIN проверяется Argon2id с солью и pepper, 5 ошибок → блок 15 мин, далее удвоение до 24 ч. SMS счётчик не сбрасывает |
| Деньги на SMS | SMS-pumping, ботнеты, перебор номеров | Allowlist стран, лимиты IP/сети/номера/устройства, глобальный лимит в час, дневной бюджет в копейках, лимит одновременных отправок. Всё в PostgreSQL, общее для экземпляров |
| Код в БД | Копия базы | В БД только HMAC-SHA256(серверный секрет, challenge‖номер‖срок‖код). Секрет вне БД. После успеха или истечения verifier стирается |
| Номер в БД | Копия базы | Хранится только HMAC номера (`PhoneIndex`). Открытого или зашифрованного номера на сервере нет |
| Доказательство входа | Перенос SMS/PIN на другое устройство, replay | Подпись ключом устройства (ECDSA P-256, Android Keystore) над payload, где есть challengeId, nonce, срок, операция, номер, deviceId, registrationId, identity key и хэш ключа подписи. Поля берутся из записи challenge, а не из запроса проверки |
| Сессия | Кража refresh token | Только verifier SHA-256 от 256-битного значения. Ротация каждый раз, повтор отзывает семью. Каждый refresh требует свежей подписи устройства, поэтому один украденный token бесполезен без ключа Keystore |
| Старый телефон | Продолжение работы после переноса | Одна транзакция: блокировка аккаунта, деактивация устройства, generation+1, отзыв всех refresh-семей, стирание недоставленного шифротекста, удаление уведомлений. JWT проверяется по БД на каждом запросе, SignalR-соединения закрываются в течение ~1 с на всех экземплярах |
| Перечисление аккаунтов | Узнать, зарегистрирован ли номер | Ответ на запрос SMS одинаков для нового и существующего номера. О наличии PIN узнаёт только тот, кто ввёл верный код |
| Логи | Утечка кода, PIN, номера, токенов, ключей | Сервер их не логирует. Ключи счётчиков — HMAC. Тест `LogsAndResponsesCarryNoSecrets` ищет эти значения во всех логах уровня Trace и в ответах |

Вне защиты: заражённый или разблокированный телефон, оператор связи, который сам выдаёт SIM и одновременно знает PIN, сервер-злоумышленник (он может подменить identity при первом контакте — защищает только сверка 60-значного кода), метаданные.

## Состояния SMS-challenge

| Состояние | Как попадает | Что разрешено | Код ошибки на verify |
| --- | --- | --- | --- |
| `Sending` | Резерв зафиксирован, SMS ещё не подтверждена провайдером или процесс упал | Ввод кода (SMS могла дойти) | — |
| `Sent` | Провайдер принял | Ввод кода | — |
| `DeliveryUnknown` | Таймаут, сеть, непонятный ответ | Ввод кода. Повторной автоматической отправки нет | — |
| `ProviderRejected` | Провайдер однозначно отказал | Ничего | `CHALLENGE_NOT_SENT` |
| `CodeVerified` | Верный код, у аккаунта есть PIN | Только `/pin/verify` с той же подписью | `CHALLENGE_USED` |
| `Completed` | Активация завершена | Ничего | `CHALLENGE_USED` |
| `Failed` | 5 неудачных попыток (код, номер, подпись) | Ничего | `CHALLENGE_LOCKED` |
| `Superseded` | Для номера создан новый challenge | Ничего | `CHALLENGE_SUPERSEDED` |
| истёк | `ExpiresAt` ≤ сейчас | Ничего | `CHALLENGE_EXPIRED` |

Refresh-challenge: `Sent` → `Completed` (успешный refresh) или `Failed` (неверная подпись). Срок 2 минуты. Тип операции хранится в записи: SMS-challenge нельзя использовать для refresh и наоборот (`CHALLENGE_NOT_FOUND`).

## Состояния сессии и переноса

| Событие | Устройство | Generation | Refresh-семьи | Access JWT |
| --- | --- | --- | --- | --- |
| Регистрация нового номера | Создано, активно | 1 | Новая семья | Выдан, `sid` = семья |
| Перенос (без PIN или с верным PIN) | Старое неактивно, новое активно | +1 | Все прежние отозваны, новая для нового устройства | Старые отклоняются сразу |
| Неверный PIN / блок PIN | Без изменений | Без изменений | Без изменений | Старый работает |
| Refresh | — | — | Старый token потреблён, новый выдан | Новый |
| Повтор потреблённого refresh | — | — | Семья отозвана | Все JWT семьи отклоняются |
| Logout | Остаётся активным | — | Семья отозвана | Отклоняется |
| Dev `replace-device` | Как перенос | +1 | Все отозваны | Старые отклоняются |

Logout не деактивирует устройство: сообщения продолжают копиться в его очереди. Новый вход на том же телефоне сейчас — это новая активация с новым deviceId; старая очередь при этом стирается. Если нужен «вход обратно в то же устройство», это отдельное решение.

## Спорные решения

1. **Отдельный ключ подтверждения вместо Signal identity.** Identity key libsignal — Curve25519, подписи XEdDSA. Проверенной серверной реализации XEdDSA для .NET нет, писать преобразование вручную запрещено заданием. Поэтому устройство создаёт в Android Keystore неэкспортируемый ключ ECDSA P-256 (`SHA256withECDSA`, поддерживается с API 23, у нас minSdk 26). Сервер проверяет его стандартным `System.Security.Cryptography.ECDsa`. Связь с Signal: identity key входит в подписанный payload и сохраняется вместе с ключом подписи в одной записи устройства. Сервер не доказывает, что identity принадлежит этому ключу Keystore. Он доказывает, что держатель ключа Keystore заявил именно этот identity. Это осознанная граница.
2. **Один глобальный advisory lock на резерв SMS.** Делает атомарными проверку idempotency, паузу 60 с, лимит одновременных отправок и все счётчики на всех экземплярах. Транзакция короткая (миллисекунды), сам вызов провайдера идёт вне неё. Для объёмов SMS этого достаточно. Если упрёмся, разделим lock по хэшу номера, а глобальные лимиты оставим на условных upsert.
3. **Неопределённый результат провайдера.** Challenge остаётся проверяемым и не отправляется повторно. Повтор того же `requestId` возвращает тот же challenge без новой SMS. Новый `requestId` даёт новую платную отправку только после паузы 60 с и в пределах лимитов.
4. **Отказанные запросы не тратят лимиты.** Счётчики увеличиваются в той же транзакции, что и резерв. Отказ одного лимита откатывает остальные. Атакующий не может «выжечь» чужую суточную квоту отказами, только успешными отправками.
5. **Неверный номер и неверная подпись тратят попытки кода.** Любое несовпадение на `/sms/verify` считается одной из пяти попыток: закрытый отказ надёжнее точной диагностики.
6. **Включение PIN требует свежей аутентификации.** Если PIN ещё не задан, `PUT /account/pin` разрешён только в течение 10 минут после SMS-активации. Иначе вор разблокированного телефона мог бы установить PIN и навсегда заблокировать владельцу перенос номера. Повторной аутентификации без переноса пока нет, позже PIN включается через `REAUTH_REQUIRED`. Смена и отключение требуют текущий PIN.
7. **Recovery code не реализован.** `POST /auth/recovery` всегда отвечает `501 RECOVERY_NOT_AVAILABLE`, `PIN_REQUIRED` возвращает `recoveryAvailable: false`. Потеря PIN блокирует перенос, обхода через поддержку или SMS нет. Предлагаемая схема на будущее: 128-битный код показывается один раз при включении PIN, на сервере только Argon2id-verifier; использование кода — альтернатива PIN на шаге `CodeVerified` и атомарно потребляет код, после чего выдаётся новый.
8. **Потерянный ответ refresh.** Повтор **того же подписанного запроса** (тот же challenge) в течение 2 минут, если выданный преемник ещё не использовался, выдаёт нового преемника, а прежний гасит. Любой другой повтор потреблённого token — reuse с отзывом семьи. Обнаружение повторного использования не отключается. Клиент обязан делать refresh в один поток (single-flight).
9. **Argon2id m=64 МиБ, t=3, p=1** (libsodium `crypto_pwhash_str`). Замер на Xeon 2,1 ГГц: хеш 91 мс, проверка 75 мс. PIN проверяется только при переносе и смене PIN, такие запросы ограничены лимитами. Не больше 4 параллельных вычислений на процесс, то есть до 256 МиБ. PIN предварительно ключуется HMAC с pepper. Копии БД без pepper недостаточно даже для перебора всего 10⁶ пространства.
10. **Нормализация номера.** libphonenumber-csharp 9.0.41, только международный ввод с `+`. Регион определяется по плану нумерации: `+7 9xx` — RU, `+7 7xx` — KZ. Принимаются только MOBILE и FIXED_LINE_OR_MOBILE. Allowlist: `Auth:Sms:AllowedRegions = RU,BY,KZ,UZ`. Каждой стране нужна цена в `Auth:Sms:CostKopecks`, иначе сервер не стартует.
11. **IP клиента.** `X-Forwarded-For` учитывается только от адресов из `Auth:TrustedProxies`, на один hop. Встроенное доверие loopback отключено. IPv6 считается по /64, подсетевой лимит — /24 для IPv4 и /48 для IPv6.

## Хранение и удаление

| Данные | Срок |
| --- | --- |
| Verifier SMS-кода | Стирается при успехе, блокировке или замене challenge, иначе фоновой очисткой после истечения (≤ 1 мин) |
| Запись challenge (HMAC номера, публичные ключи, состояние) | Удаляется через 24 ч после `ExpiresAt`. Нужна для idempotency, паузы 60 с и разбора инцидентов |
| Счётчики лимитов | Удаляются после конца окна |
| Refresh token verifier | 30 дней неактивности, удаление через 1 день после истечения |
| Refresh-семья | Абсолютный срок 90 дней. Удаляется через 1 день после него или через 30 дней после отзыва |

## Известные ограничения

- Контракт SMS.ru сверен по вторичным источникам. Официальная документация из среды разработки была недоступна. Перед любой платной отправкой нужна сверка: параметры, коды ошибок, тестовый режим, ограничения отправителя.
- Цены в `CostKopecks` — заглушки для бюджета, их надо заменить тарифом SMS.ru по каждой стране.
- Текст SMS только на русском, без Android SMS Retriever hash.
- Нет повторной аутентификации существующей сессии и recovery code.
- Нет автоматической остановки отправок по аномалии (рост доли непроверенных кодов): есть только жёсткие лимиты и бюджет.
- Ответы `ApiFault` пишутся в лог уровня Error стандартным обработчиком исключений ASP.NET: только код ошибки и стек, без данных запроса. Это шумно, но не раскрывает секреты.
- Юридическая готовность не следует из размещения сервера в России. До запуска с реальными номерами нужна отдельная проверка: 152-ФЗ (номер — персональные данные, локализация, уведомление РКН, политика), требования к организаторам распространения информации, согласие на SMS, договор с SMS.ru и регистрация имени отправителя, условия стран BY/KZ/UZ, правила Google Play о данных и SMS.
