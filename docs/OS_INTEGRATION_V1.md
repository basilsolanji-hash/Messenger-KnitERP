# Ось коммуникации: подключение к системе «Ось»

Статус: проект контракта для реализации. Описанные ниже `/integrations/os/*` endpoints ещё не реализованы. Существующий API доставки зашифрованных сообщений продолжает работать отдельно. Дата: 22 октября 2026 года.

## Название и совместимость

Экосистема — **Ось**, мессенджер — **Ось коммуникации**, прежний бренд — knitERP. Обновлены название приложения, заголовок и новые демонстрационные тексты в ru/be/kk/uz. До подключения утверждённого графического знака интерфейс использует текстовое название «Ось».

Технические идентификаторы сохраняются: Android package/applicationId, URI/протокольные версии, Keystore aliases, имена БД и профилей, JWT issuer/audience и строки канонической подписи. Их массовая замена сломает совместимость и доступ к истории. Существующие сообщения не переписываются из-за ребрендинга. Переименование репозитория и домена в эту поставку не входит.

## Что связываем в первой версии

1. Сотрудник в «Ось» ↔ существующий аккаунт мессенджера, после подтверждения самим сотрудником.
2. Карточка заказа, производственного задания или документа ↔ ссылка на контекст обсуждения.
3. Из карточки объекта — переход в мессенджер; из сообщения со ссылкой — открытие объекта в «Ось» с её собственной проверкой доступа.

Группы по подразделениям/заказам, автоматическая запись всех сотрудников в чат и системный бот не входят в первый API: групповые чаты ещё не реализованы.

## Граница работы

Разрабатываем только приложение «Ось коммуникации», его сервер и внешний API. Основную систему «Ось», её код и БД не меняем. Доступ к её репозиторию не является условием подготовки API мессенджера.

Внешняя команда реализует адаптер по опубликованному контракту: передаёт собственные стабильные непрозрачные IDs сотрудников и объектов и сопоставляет свои роли с выданными scopes. Внутренние таблицы и формат сессий ERP не становятся зависимостью мессенджера. Пароли и API-ключи не передаются в чат.

Сейчас проверен сервер мессенджера и его действующая авторизация. Документ `OS_INTEGRATION.openapi.yaml` фиксирует предварительный внешний контракт. Его наличие не означает, что новые маршруты уже реализованы или проверены совместно с внешней системой.

## Разделение авторизации

- Сервис «Ось» использует отдельную учётную запись интеграции с коротким токеном, ограниченными scopes и привязкой к одной организации. Выдачу, ротацию и отзыв служебных credentials обеспечивает сервер мессенджера; этот модуль пока не реализован. SSO основной системы не является обязательным условием подключения.
- JWT телефона подтверждает владельца аккаунта мессенджера. Токен интеграции не может притвориться телефоном, читать inbox, получать prekeys от имени пользователя или отправлять сообщения от его имени.
- `tenantId` берётся из проверенной серверной связи credentials → организация. Поле из запроса не может сменить tenant. Нужны отдельные миграции для организаций и связей — сейчас эта модель отсутствует.
- Номер телефона, имя и одинаковый email не являются достаточным основанием автоматически связать аккаунты.
- Административный provisioning secret не используется для интеграции и не передаётся в ERP/browser/Android.

## Предварительный HTTP-контракт v1

Префикс — `/api/v1/integrations/os`. JSON UTF-8; HTTPS обязателен. Это согласуемые маршруты, не реализованная функциональность.

| Метод и маршрут | Кто вызывает | Назначение |
| --- | --- | --- |
| `POST /link-challenges` | Сервис «Ось» | Создать одноразовый запрос связи для `externalUserId`, подтверждённого сессией пользователя в ERP |
| `POST /link-challenges/{challengeId}/preview` | Авторизованный телефон | Проверить секрет и получить данные организации для экрана согласия без потребления запроса |
| `POST /link-challenges/{challengeId}/confirm` | Авторизованный телефон | Явно подтвердить связь своим аккаунтом и одноразовым секретом запроса |
| `GET /users/{externalUserId}/link` | Сервис «Ось» | Получить состояние связи только пользователя своей организации |
| `DELETE /users/{externalUserId}/link` | Сервис «Ось» | Отозвать связь и доступ интеграции к ней |
| `DELETE /me/links/{linkId}` | Авторизованный телефон | Самостоятельно отключить связь с указанной доступной ему интеграцией |
| `POST /references` | Сервис «Ось» | Зарегистрировать непрозрачную ссылку на доступный бизнес-объект |
| `GET /references/{referenceId}` | Авторизованный телефон | Разрешить ссылку после проверки организации, связи и явного списка получателей |
| `DELETE /references/{referenceId}` | Сервис «Ось» | Отозвать ссылку своей организации, не удаляя переписку или объект |

Сервисные scopes: `links:write`, `links:read`, `references:write`, выданы только для согласованной организации. Телефон не может выдать эти права себе. `externalUserId`, `externalObjectId` — непрозрачные стабильные идентификаторы, их значения определяет внешняя система; API принимает ограниченные по длине строки и не разбирает их внутреннюю структуру.

### Связь аккаунтов

Запрос: `{ "externalUserId": "opaque-erp-user-id" }`, обязательный `Idempotency-Key` UUID в заголовке. Сервер создаёт случайный 256-битный confirmation secret, хранит только verifier, TTL 5 минут. В пределах TTL повтор с тем же Idempotency-Key и телом возвращает тот же ответ, не создавая второй запрос. Для этого ответ с секретом временно хранится только в виде шифротекста под серверным Data Protection; ключи защиты расположены отдельно от БД. Открытый секрет не хранится и не логируется. После потребления/истечения ответ удаляется и повтор возвращает 409/410 без секрета. Одноразовое потребление подтверждения не означает запрет безопасного повтора выдачи того же ещё не использованного challenge.

Телефон показывает, какую организацию и учётную запись пользователь связывает. Подтверждение потребляет запрос атомарно, проверяет сроки, tenant, текущий аккаунт, активность устройства, а для чувствительного связывания — свежесть аутентификации. Подтверждение сервисным токеном или одним совпадением номера запрещено. Конкурирующие подтверждения создают не более одной связи. Ошибки и лимиты не раскрывают аккаунты других организаций.

Ответ статуса: `linkId`, `externalUserId`, `messengerAccountId`, `state`. Телефон, identity key, токены, последнее посещение и история в ответ не входят. Уникальность связи: tenant + externalUserId; изменение существующей связи требует явного отзыва и нового подтверждения.

Удаление сотрудника в ERP отключает соответствующую связь и интеграционные права. Оно не удаляет личный аккаунт мессенджера, его другие связи и историю. Отзыв связи проверяется на каждом разрешении ссылки, а не только в интерфейсе.

### Ссылки на объекты

Запрос: `{ "kind": "order", "externalObjectId": "opaque-order-id", "audienceExternalUserIds": ["opaque-user-id"] }`. Список audience обязателен, 1–256 уникальных внешних пользователей своей организации, и не создаёт групповой чат. Разрешение ссылки требует активной связи пользователя и совпадения его externalUserId с audience. Отозвать доступ ко всей ссылке можно DELETE; изменение аудитории в v1 — отзыв и создание новой ссылки. Начальный allowlist: `order`, `production_task`, `document`. Идемпотентность ограничена организацией и телом запроса. Ответ: случайный непрозрачный `referenceId`; предсказуемый ID заказа не используется как секрет доступа.

Цена, заказчик, зарплата, описание задачи, документы и текст сообщения через этот API не передаются. Сервер хранит только минимально необходимые метаданные связи. Они тоже не считаются полностью анонимными.

Подтверждённый домен deep links/App Links определяется настройкой сервера мессенджера. Внешняя система сама проверяет права на бизнес-объект, мессенджер — права на связь и организацию. Не внедрять вымышленные рабочие URL или произвольный redirect из тела запроса. Вход по ссылке не обходит авторизацию в ERP. Если связь/права отозваны, доступ закрывается. Права на сам заказ всегда повторно проверяет ERP.

## Сквозное шифрование и системные сообщения

API интеграции не получает открытый текст чатов, ключи расшифровки, поисковый индекс переписки или экспорт всей истории. Не добавлять `/send-text` на сервер мессенджера, принимающий plaintext, под видом E2EE.

Обычный сотрудник отправляет ссылку и текст внутри уже зашифрованного Signal-сообщения. До изменения wire schema используется только поддерживаемый согласованный формат; версия Content не расширяется молча.

Если нужны системные уведомления («заказ просрочен», «назначено задание»), отдельный доверенный отправитель на стороне ERP становится явным участником переписки со своими ключами и шифрует сообщения до сервера мессенджера. ERP при этом знает созданный ею текст как отправитель; нельзя утверждать, что она его не знает. Это отдельная следующая задача, не готовая функция v1.

Серверу нельзя выдавать приватные ключи сотрудников. Токен интеграции не даёт права расшифровывать сообщения. Push содержит только сигнал о наличии очереди, без бизнес-данных и текста; FCM ещё не подключён.

## Надёжность и приёмка

- Идемпотентность scoped по tenant; тот же ключ с другим телом → 409. Ретраи с ограничением и задержкой; 429 с Retry-After. Точные retention и пределы запросов фиксируются до реализации.
- Отдельные лимиты на организацию, credentials и запросы подтверждения. Логи содержат correlation ID и результат, без секретов, номеров, текста и содержимого объектов. Ошибки: стабильный `code`, без сырых ответов ERP.
- Проверки: две организации с одинаковыми external IDs; чужие IDs; истёкший/повторный challenge; гонка связи; смена сотрудника/прав; отзыв интеграции; повтор запроса; недоступность ERP; неизвестный тип объекта; запрещённый redirect. Проверяются серверные ответы, а не только скрытие кнопки.
- Миграции сохраняют существующие ключи, аккаунты, inbox/outbox. При ошибке интеграция останавливается, история и ключи не сбрасываются.
- Предварительный контракт представлен в `OS_INTEGRATION.openapi.yaml`; перед реализацией фиксируются его версия, машинные ошибки и протокол выдачи служебных токенов. Нужны контрактные тесты с независимым тестовым клиентом внешней системы и отдельный тест двух телефонов.

Готовность этой поставки: текстовый ребрендинг в Android-коде и проект интеграционного контракта. Нового APK, реализованных integration endpoints, SSO или фактического подключения ERP эта поставка не подтверждает.
