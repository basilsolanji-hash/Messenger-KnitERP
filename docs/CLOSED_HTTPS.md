# Закрытый HTTPS для «Ось коммуникации»

Подготовка конфигурации ещё не означает развёртывание. Публичный домен/VPS, настоящий сертификат, доступ с телефонов и восстановление базы пока не проверены. Существующий Development-only guard сохраняется. Основная ERP не затрагивается.

## Схема

Выделенный экземпляр Nginx принимает HTTPS и передаёт запросы только в API на `127.0.0.1:5080`. Существующий Compose публикует API только на loopback, PostgreSQL остаётся внутри Docker. Для этого закрытого стенда Nginx работает одним процессом; производительность на 10 000 пользователей этим не подтверждается.

Используйте **полный сгенерированный nginx.conf** как отдельную конфигурацию. Не подключайте nginx-http.conf к уже настроенному HTTP-контексту другого сайта: унаследованные real_ip, маршруты, журналы или TLS могут изменить проверенное поведение. CDN/балансировщик перед этим Nginx в текущую схему не входят: allowlist использует прямой TCP IP. На одном адресе/порту нельзя одновременно запускать другой HTTPS listener; чужой сайт не останавливать ради проверки.

Разрешённые тестировщики получают `/api/v1/*` и `/hubs/events`. Отдельная allowlist операторов получает `/api/v1/dev/*`, `/openapi/*` и `/health/*`. Остальным IP — отказ. Оператор, которому нужны обычные пользовательские методы, отдельно включается и в список тестировщиков. Отсутствие списка операторов закрывает эти пути всем. Не используйте общую публичную сеть как allowlist; при меняющемся мобильном IP нужен контролируемый VPN или актуальный внешний IP.

Операторские пути выделены регулярными выражениями без учёта регистра раньше обычного API: ASP.NET сопоставляет маршруты без учёта регистра. Проверяются также кодирование символов, двойные слеши и относительные сегменты. Входящий X-Forwarded-For заменяется IP прямого клиента; автоматические повторы proxy отключены. Access log отключён, error log ограничен уровнем crit. Не включайте debug/body/header logging с рабочими секретами.

## Подготовка файлов

Нужны Python 3.10+, OpenSSL, Nginx с SSL/access/proxy/regex модулями и действующий сертификат с DNS SAN. Проверено локально на Ubuntu Nginx 1.24.0, OpenSSL 3.0.13. Установленная на VPS версия требует отдельного `nginx -t` и приёмки.

Оператор предоставляет текущую цепочку PEM, соответствующий незашифрованный TLS key и **публичный сертификат отдельного резервного ключа**. Резервный приватный ключ хранится отдельно, генератору он не нужен. Генератор проверяет hostname/SAN/срок текущего сертификата, соответствие ключа и различие двух SPKI. Проверка доверия публичному CA/полноты цепочки и владения резервным ключом выполняется отдельно. Self-signed сертификаты допустимы только в локальном тесте с собственной временной CA; в системное хранилище Android её не добавлять.

Пример с вымышленным доменом и документационными IP — заменить своими значениями. Пути должны содержать только ASCII-буквы, цифры, `/._-`. Выходной каталог должен быть новым и находиться сразу по окончательному пути: конфигурация содержит абсолютные ссылки.

```bash
python3 scripts/prepare-closed-https.py \
  --hostname messenger.example.com \
  --certificate /etc/os-communications-tls/fullchain.pem \
  --private-key /etc/os-communications-tls/current.key \
  --backup-certificate /etc/os-communications-tls/backup-public.pem \
  --tester 198.51.100.10/32 \
  --operator 203.0.113.20/32 \
  --bind 0.0.0.0 \
  --output /etc/os-communications-https-v1
```

Без `--bind` listener привязан к `127.0.0.1`. По умолчанию HTTPS порт 443, upstream порт 5080. Генератор не меняет DNS, firewall, сертификаты, сервисы и существующие файлы. Он не копирует приватный ключ и не выводит секреты. Создаёт каталог 0700, файлы 0600 и приватный runtime-каталог:

- `nginx.conf` — самостоятельная конфигурация для выделенного процесса.
- `nginx-http.conf` — внутренний include только для этого nginx.conf.
- `server-endpoint.json` — только `{origin,pins}`, без operator/bearer/password.
- `pins.json` — тот же массив leaf SPKI pins для существующего provision-phone.py.
- `runtime/` — PID, критические ошибки и временные файлы Nginx.

JSON с публичными pins можно передавать тестировщикам по проверенному каналу. Не отправлять им каталог конфигурации, TLS key, `.env`, сессии другого телефона или операторский ключ. Сертификат с тем же ключом, выданный заново, не считается резервным: pins должны отличаться. Смена обоих pins в активном Android-профиле не поддерживается — существующее ограничение клиента сохраняется.

## Перед запуском на VPS

Подготовьте отдельного непривилегированного системного пользователя для HTTPS. Ему нужны чтение обоих конфигурационных файлов, текущего сертификата/key и запись только в runtime. Закрытые каталоги должны допускать проход именно этому пользователю; права для всех не открывать. Для порта 443 дайте только CAP_NET_BIND_SERVICE через отдельный systemd unit, без запуска Nginx как root. Unit/права/boot restart здесь пока не проверены. На высоком порту локальный тест выполняется без capabilities. Сами конфиги после проверки должны быть доступны процессу только на чтение.

Сначала от имени этого пользователя, с тем же доступом к файлам **и той же capability, что у unit**, проверьте:

```bash
systemd-run --quiet --wait --pipe --collect -p User=os-closed-https -p Group=os-closed-https \
  -p AmbientCapabilities=CAP_NET_BIND_SERVICE -p CapabilityBoundingSet=CAP_NET_BIND_SERVICE -p NoNewPrivileges=yes \
  /usr/sbin/nginx -t -p /etc/os-communications-https-v1/ -c /etc/os-communications-https-v1/nginx.conf
```

`nginx -t` открывает listen-сокеты. Без capability непривилегированный пользователь получает `bind() to 0.0.0.0:443 failed (13: Permission denied)` и `test failed` даже при верном синтаксисе. Так было при приёмке на VPS 25.10.2026 (Nginx 1.28.3). Занятый работающим экземпляром порт в режиме проверки nginx игнорирует, а отказ в правах — нет. Строка `[alert] could not open error log file` про `/var/log/nginx/error.log` относится к журналу пакета до чтения конфигурации; собственный журнал стенда находится в `runtime/`. Эта команда только проверяет конфигурацию и может создать runtime-файлы; не включает стенд. Готовая последовательность смены allowlist с проверкой и откатом: `deploy/closed-stand/set-allowlist.sh`. После подготовки unit запускать нужно с теми же `-p`/`-c`, nginx.conf уже задаёт foreground/single-process. Нельзя использовать глобальный nginx reload: он относится к другому процессу. При обновлении создайте новый каталог, повторите проверки и переключайте только выделенный unit; старые ключи/каталог сохраняйте до подтверждённого отката.

В API установить `AllowedHosts` точно в выбранный hostname. Если операторский fake-SMS/provisioning сценарий нужен, отдельно установить `Dev__EnableOperatorEndpoints=true` и сильный `Dev__ProvisioningKey`. По умолчанию маршруты отсутствуют; Nginx их не создаёт и не отменяет проверку секрета. Провайдер остаётся Fake до отдельной проверки тарифа/бюджета и решения о реальных SMS.

`Auth__TrustedProxies__0` должен быть **фактическим единственным peer IP Nginx, наблюдаемым API**. При host Nginx → Docker published loopback это может быть gateway Docker, а не 127.0.0.1. Определить адрес по реальной топологии и подтвердить, что поддельные заголовки не влияют на IP-лимиты. Не доверять подсетям/всем адресам. Пустой список безопасно игнорирует заголовки, но тогда SMS IP-лимит будет общим для прокси. Изменение Docker-сети требует повторной проверки. API/БД наружу не открывать.

Снаружи по исходному ТЗ только 443 и SSH 22 с ключами; сертификат можно получать/продлевать через DNS-проверку без нового HTTP listener. Правила firewall и выпуск сертификата здесь не выполняются.

## Воспроизводимые локальные проверки

Тесты не обращаются к SMS.ru, настоящей PostgreSQL или системному CA store. Нужен установленный тестовый Nginx; отсутствие binary — ошибка, не пропуск теста:

```bash
NGINX_BINARY=/usr/sbin/nginx python3 -m unittest discover -s scripts/tests -v
```

Проверяются генератор, приватные права, отсутствие копии key, отказ от перезаписи, реальный локальный TLS, текущий/неверный pin через curl, запреты IP и пути операторов. Тестовый upstream — простой HTTP fixture, не API и не база. В среде UID0 без capabilities тестовая команда добавляет `user root;` только к локальному Nginx, чтобы избежать chown на недоступный nobody. Сгенерированная конфигурация эту директиву не содержит и рассчитана на запуск отдельным непривилегированным пользователем.

Перед реальной перепиской остаются: PostgreSQL-регрессия, HTTPS с публичной CA и точными pins с обоих физических телефонов, отрицательные проверки IP/TLS, восстановление зашифрованной backup в отдельную БД, SMS/PIN/refresh и текст в обе стороны с отключением сети/перезапуском. До этого стенд не считать принятым.

Основания настроек: официальные документы Nginx [access](https://nginx.org/en/docs/http/ngx_http_access_module.html), [location](https://nginx.org/en/docs/http/ngx_http_core_module.html#location), [proxy](https://nginx.org/en/docs/http/ngx_http_proxy_module.html), [SSL](https://nginx.org/en/docs/http/ngx_http_ssl_module.html).
