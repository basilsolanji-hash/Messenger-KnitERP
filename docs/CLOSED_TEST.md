# Закрытый сетевой тест 0.2

Это операторский стенд для синтетических данных. Он не заменяет SMS-регистрацию, PIN, refresh rotation или подтверждение владения устройством. Предохранитель `Development` остаётся включённым. Публичный запуск и переписка двух физических телефонов ещё не проверены.

## Что подключено

В Android: «Настройки → Закрытый тест сервера». Сетевой профиль отделён от двух локальных демонстрационных профилей. Все приватные ключи Signal, сессия и история сохраняются в SQLCipher/Room. Секрет сессии вводится в скрытое поле и не сохраняется в состоянии Activity.

У каждого телефона свои ключи и индивидуальная сессия на 15 минут. APK не содержит административного ключа. Приложение проверяет `/me`: аккаунт, устройство, generation, registrationId, публичный identity key и срок сессии. Сессия для других ключей не подключается.

Соединение требует HTTPS, системного доверия сертификату, совпадения имени хоста и 2–5 SHA-256 SPKI pins для этого хоста. Нужны текущий и резервный публичные ключи сертификатов. Обход TLS и переходы по redirect отсутствуют. Перед первым запросом интерфейс показывает сервер. После подключения профиль закрепляет origin и набор pins; смена сервера/набора pins отклоняется до отправки токена. Поток безопасной ротации pins пока отсутствует.

Доставка запускается кнопкой «Синхронизировать» или после отправки. За проход обрабатывается до 20 исходящих сообщений и до трёх страниц inbox. Для большего объёма нажмите синхронизацию повторно. FCM, фоновая доставка и Android-клиент SignalR пока не подключены.

## Подготовка оператором

Нужен отдельный доступный тестовым телефонам HTTPS-стенд с доверенным сертификатом, ограниченным доступом, текущим и резервным leaf SPKI pins. Локальный `docker compose` открывает только HTTP на loopback и сам по себе для Android-сценария не подходит. Beget, домен и TLS ещё не настроены.

1. На каждом телефоне создайте публичный запрос с тестовым именем. Скопируйте JSON в отдельный `*.enrollment.json` в `.secrets/`. Запрос содержит только имя, deviceId, registrationId и публичный identity key, без приватных ключей.
2. Оператор готовит `pins.json`: JSON-массив из строк вида `sha256/BASE64_SHA256_SPKI`. CLI и Android должны использовать одинаковый набор. Для совместимости CLI pins относятся к ключам leaf-сертификатов.
3. Задайте `DEV_PROVISIONING_KEY` в приватном окружении оператора. Не передавайте его в аргументах команд, приложении или конфигурации телефона. Затем из корня репозитория:

```bash
python3 scripts/provision-phone.py \
  --origin https://YOUR_TEST_HOST \
  --pins-file .secrets/pins.json \
  --request .secrets/alice.enrollment.json \
  --output .secrets/alice.session.json
```

Скрипт использует curl с обычной проверкой CA/hostname и обязательным pinning, без redirect. Секретный административный заголовок передаётся curl через stdin, а не argv. Индивидуальная сессия записывается с правами `0600`; существующий файл не перезаписывается. В stdout выводится публичный account ID, без токена. Нужен curl с поддержкой `--pinnedpubkey`.

4. Передайте содержимое `alice.session.json` только телефону Alice, запрос которого использовался при выдаче. Вставьте JSON в скрытое поле, проверьте показанный адрес сервера и подключите сессию. Повторите отдельно для Bob. Приватные ключи не экспортируются.
5. Обменяйтесь публичными UUID аккаунтов, откройте чат по UUID, отправьте тестовое сообщение, на адресате нажмите «Синхронизировать». После ответа сравните все 60 цифр кода безопасности на обоих телефонах по независимому каналу.
6. После истечения 15 минут оператор повторяет команду с тем же публичным запросом и `--account-id UUID_ЭТОГО_АККАУНТА`, задавая новый `--output`. Endpoint `/api/v1/dev/accounts/{id}/session` выдаёт сессию только при совпадении активного устройства и ключей; устройство не заменяется. Импортируйте новую сессию в том же приложении. Это не пользовательский refresh flow.

Файлы `*.session.json`, `*.enrollment.json`, `.secrets/` и `.env` исключены из git. Не используйте общие сессии для разных телефонов.

## Поведение при сбоях

- Отправка сначала атомарно сохраняет ratchet, историю и неизменяемый шифротекст в локальный outbox. Потеря HTTP-ответа повторяет тот же конверт; сервер удаляет дубли по clientMessageId.
- ACK отправляется после COMMIT расшифровки, истории и ratchet. Потеря ACK приводит к повторной выдаче и локальной дедупликации. Ошибка хранилища не считается подтверждённым приёмом.
- Известные ошибки проверки конверта/identity не подтверждаются; соседние корректные сообщения могут быть приняты. Неизвестные ошибки прерывают проход без ACK для ещё не подтверждённого пакета.
- Курсор inbox не сохраняется между проходами: неподтверждённые сообщения повторяются после перезапуска.
- Истёкшая/отозванная сессия останавливает сетевой обмен. Локальная очередь сохраняется. Смена identity или устройства останавливает переписку, автоматического доверия новому ключу нет.
- Максимум 1000 ожидающих исходящих сообщений. История пока читается без пагинации. При незавершённом установлении сессии claim хранится локально; автоматическое восстановление claim после серверного TTL 24 часа ещё не реализовано.
- Начальные одноразовые ключи публикуются при импорте сессии. Если публикация прервалась, повторите импорт той же сессии; безопасное автоматическое пополнение и ротация ещё нужны.

## Критерий фактического теста двух телефонов

Проверить отдельные установки ARM64: первый обмен и совпадение safety number, адресат офлайн, повтор после потери сети, остановка и запуск процесса, повторный импорт сессии, её отзыв, неверный сертификат и смена ключей. JVM-тест, эмулятор одного телефона или экран настройки не закрывают этот критерий.
