## Исходное состояние

- В `main` есть workflow `Android emulator instrumentation`: 6 наборов тестов на эмуляторах API 26 и API 36 x86_64 с настоящими Keystore, SQLCipher и libsignal. Начать с его фактического результата; если красный — исправить причину, а не отключать тест.
- Вход SMS/PIN, единый application owner/UserSession, журнал подготовки профиля, `/me` → bind → publish → readiness, logout до HTTP уже в коде; на эмуляторе и с живым API не проверены.

## Приёмка

1. Instrumentation зелёный на API 26 и API 36 в CI. Добавить тесты, где сценария нет, а не дублировать реализацию.
2. Один application owner/UserSession при навигации, повороте, двух ViewModel и process death. Отдельный профиль на каждую активацию; повтор подготовки сохраняет прежний deviceId и ключи.
3. Вход с Fake SMS: код выдаёт оператор вне APK. Повтор через 60 секунд и Retry-After; неверный, истёкший, исчерпанный код; PIN_REQUIRED/PIN_LOCKED; установка, смена, отключение PIN; logout; перенос на новый телефон с отзывом старого.
4. Секреты не попадают в SavedState, Intent, clipboard, логи и снимки экрана.
5. Переписка: текст в обе стороны, офлайн-очередь, потеря ответа send/ACK, повтор без дублей, перезапуск, refresh, отзыв устройства. Смена identity собеседника не принимается молча.
6. Четыре языка RU/BY/KZ/UZ (латиница), узкий экран. UUID собеседника и ручная синхронизация допустимы; контакты по номеру и автообновление не выдавать за готовые.
7. Живой API: после получения `server-endpoint.json` от задания 01 — вход и переписка через закрытый HTTPS с проверкой CA, hostname и SPKI pins. TLS-проверки не отключать, operator/provisioning secret в APK не добавлять.
8. Два физических телефона: составить чек-лист ручной проверки для пользователя (установка нужного ABI APK, вход, переписка, офлайн, перезапуск, перенос) и записать фактические результаты с его слов.
