# Панель администратора сервиса — требования, архитектура, безопасность

Этапы 1–4 процесса «Ось-ERP · От задачи до выпуска» для раздела 17 ТЗ (`PRODUCT_SPEC.md`), часть «Панель администратора сервиса». Операторская панель стенда уже сделана отдельно: `server/Messenger.Api/OperatorPanel.cs`. Связь с «Ось» — следующим пакетом.

Статус: макеты утверждены владельцем 5 ноября 2026 года. Первая поставка реализована, API описан в `ADMIN_API.md`. Жалобы ждут клиентской функции «Пожаловаться».

## 1. Требования

**Цель:** администратор управляет пользователями и жалобами, не видя переписки.

**Граница:**
- Только веб-панель на сервере мессенджера.
- Без доступа к тексту, вложениям, ключам, PIN и кодам SMS.

**Критерии завершения:**
- Вход по логину, паролю и коду TOTP.
- Роли проверяет сервер.
- Каждое действие пишется в журнал.
- Все проверки из раздела «Приёмка» ниже проходят тестами.

Функции первой поставки:

| Раздел | Что видно | Что можно сделать | Роли |
|---|---|---|---|
| Пользователи | accountId, дата регистрации, способ входа (SMS или синтетический), число устройств, активное устройство и его поколение, PIN вкл/выкл, состояние (активен / приостановлен) | приостановить и возобновить аккаунт (все сессии отзываются, вход и доставка запрещены), отозвать сессии | просмотр — поддержка, аудитор (только журнал); действия — администратор |
| Жалобы | дата, на кого, категория, сообщения, которые пожаловавшийся сам переслал (раздел 12 ТЗ) | закрыть без мер, приостановить аккаунт | администратор |
| Метрики | активные устройства, очередь доставки, ошибки API за час, расход и бюджет SMS | — | все роли |
| Журнал | кто, когда, IP, действие, объект, результат | фильтр, выгрузка CSV | аудитор, администратор |
| Учётные записи панели | логины, роли, второй фактор настроен, блокировка | создать, сменить роль, заблокировать, сбросить TOTP | администратор |

Номер телефона сервер не хранит: только HMAC (`PhoneIndex`). Поэтому «полный номер по отдельному действию» из раздела 17 в первой поставке невозможен. Поиск идёт по полному номеру: администратор вводит номер, сервер считает HMAC и находит аккаунт. Номер при этом не записывается в журнал, туда попадает только факт поиска.

Жалобы требуют клиентской функции «Пожаловаться» (раздел 12), которой ещё нет. Пока функции нет, раздел панели будет пустым.

## 2. Планирование

1. Утверждение макетов (этап 5) — владелец.
2. Модель данных и миграция:
   - `admin_users`, `admin_sessions`, `admin_audit`;
   - поле `accounts.SuspendedAt`;
   - `reports` — вместе с клиентской жалобой.
3. Вход, сессии, роли, журнал — сервер и тесты PostgreSQL.
4. Пользователи, метрики, журнал — API и страница.
5. Приостановка аккаунта: проверка в `Access` и `Transport`, тесты.
6. Ревью, аудит, прогон, сборка, приёмка по чек-листу.

## 3. Архитектура

- Тот же процесс ASP.NET, маршруты `/admin` (страница) и `/api/v1/admin/*` (данные). Включаются отдельным флагом `Admin:Enabled=true`. Без флага маршрутов нет (404), как у операторских путей.
- Снаружи доступ только через Nginx: отдельный `location` со списком IP администраторов (в `prepare-closed-https.py` — новый список `--admin`). Для рабочего сервера дополнительно WireGuard.
- **Сессия:**
  - cookie `__Host-os-admin`: `Secure; HttpOnly; SameSite=Strict; Path=/`;
  - в базе хранится SHA-256 токена;
  - срок 30 минут без действий, 8 часов максимум.
- **CSRF:** каждый изменяющий запрос несёт заголовок `X-Admin-Csrf`, который равен токену из ответа `/api/v1/admin/me`. Сервер проверяет его вместе с `Origin`.
- **Пароль:** Argon2id (как PIN, libsodium), не короче 12 символов. После 5 ошибок — блокировка на 15 минут, учитывается логин + IP.
- **TOTP:** RFC 6238, SHA-1, 6 цифр, шаг 30 с, окно ±1.
  - Секрет зашифрован Data Protection.
  - Повтор того же кода в окне запрещён.
- **Первая учётная запись** создаётся только командой на сервере: `dotnet Messenger.Api.dll admin create --login … --role admin`. Команда печатает секрет TOTP один раз, в виде QR в терминале и строки `otpauth://`. Через веб первую учётную запись создать нельзя.
- **Журнал `admin_audit`:** только добавление. Роль базы данных API не имеет `UPDATE`/`DELETE` на эту таблицу — отдельная миграция прав. Записи хранятся 1 год.
- **Ответы:** без номеров (кроме маски), токенов, ключей и шифротекстов. Тест проверяет это для каждого ответа.

## 4. Безопасность (угрозы → меры)

| Угроза | Мера |
|---|---|
| Подбор пароля | Argon2id, блокировка, лимит по IP, список IP в Nginx |
| Кража пароля | второй фактор TOTP обязателен, без него вход невозможен |
| Кража cookie | HttpOnly, Secure, короткий срок, привязка к IP-сети /24 (предупреждение и выход при смене) |
| CSRF | SameSite=Strict, заголовок `X-Admin-Csrf`, проверка `Origin` |
| XSS | CSP `default-src 'none'; script-src 'self'`, DOM только через `textContent` |
| Злоупотребление администратором | роли, журнал без возможности правки, выгрузка журнала аудитором |
| Утечка переписки | сервер её не имеет (E2EE); API панели не читает `envelopes.Ciphertext` — тест |
| Перебор аккаунтов по номеру | поиск по номеру с лимитом 20 в час на учётную запись, факт поиска в журнале |

## Приёмка (этап 13)

Тесты PostgreSQL:
- без флага все маршруты отвечают 404;
- без TOTP вход невозможен;
- неверный TOTP и повтор кода отклоняются;
- без CSRF изменяющий запрос получает 403;
- роль «поддержка» не может приостановить аккаунт;
- приостановленный аккаунт получает 401 на `/me` и не может войти по SMS;
- доставка ему возвращает 403;
- каждое действие появляется в журнале;
- ни один ответ панели не содержит токенов, номера и шифротекста.

Ручная проверка — по макетам на трёх ширинах.
