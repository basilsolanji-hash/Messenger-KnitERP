# Проверка и объединение клиентской авторизации

Дата: 23 октября 2026 года. Исходные ветки: клиентский PR #3 (`686c241`) и сетевой PR Claude #4 (`e78d48a`). Сервер и основная система «Ось» в рамках исправлений не переписываются; серверные изменения PR #4 сохраняются при объединении без изменений.

## Исправления

### Потерянный refresh нельзя молча заменить новым challenge

В исходном `UserSession.refresh()` старый pending-запрос отбрасывался после 110 секунд, после чего создавался новый challenge с тем же refresh token. Если первый запрос уже выполнился, такой запрос приводит к отзыву семейства как reuse. Аналогичная неоднозначность есть при отсутствии прежнего challenge: ответ CHALLENGE_NOT_FOUND не доказывает, что токен никогда не потреблялся.

Теперь точные байты и бюджет попыток сохраняются до HTTP. После одного потерянного ответа разрешён один идентичный повтор, включая перезапуск объекта/процесса. Истечение окна, перевод часов назад, несовпадение tokenId и неоднозначное состояние останавливают обновление с явной причиной, без нового challenge со старым токеном. Токен и pending-запрос удаляются из auth-состояния, но Signal-история и outbox не затрагиваются.

Только CHALLENGE_EXPIRED допускает новую challenge: текущая серверная реализация возвращает этот код после ветки consumed-token, то есть для непотреблённого токена. Эта зависимость от v1-контракта зафиксирована в коде; произвольная смена серверного поведения потребует пересмотра.

Новые клиентские причины: REFRESH_RECOVERY_EXPIRED, REFRESH_RETRY_EXHAUSTED, REFRESH_OUTCOME_UNKNOWN. Будущий UI должен показывать необходимость нового входа и сохранять прежний профиль только для чтения. Автоматического сброса Signal-ключей нет. Блокировка синхронизации по `@Synchronized` действует на один экземпляр UserSession; будущая Android-точка входа обязана владеть ровно одним экземпляром на активный профиль. Глобальное управление экземплярами пока не подключено.

### Ответ проверяется до удаления recovery journal

Прежний код сохранял новую пару до разбора expiresAt. Неверная дата могла удалить recovery journal до того, как ответ пригоден к использованию. Теперь формат токенов, UUID, привязка к устройству, generation и даты проверяются перед COMMIT; access публикуется после успешного сохранения. `install()` принимает только уже сохранённую пару. Сбой хранения или неверный ответ оставляет прежний запрос доступным для безопасного повтора в пределах бюджета.

### Номер и диагностические данные

PhoneInput отклоняет Unicode-цифры, лишний/внутренний `+` и международный префикс, не совпадающий с выбранной страной. Прежде часть таких значений могла интерпретироваться заново как национальный номер. Окончательную проверку плана нумерации по-прежнему выполняет сервер.

SmsChallengeRequest получил redacted toString: номер больше не попадает в автоматически сгенерированную строку DTO. Неправильные типы полей Problem Details не превращаются в исключение парсера с сырым телом; поддержан числовой Retry-After.

### Один построитель подписываемых байтов

Kotlin DeviceProof делегирует строгому DeviceProofPayload.java из PR #3. Это устраняет два независимых построителя одного протокола. Android DeviceAuthKey реализует DeviceSigner, сохраняя неэкспортируемый ключ и прежние aliases. Пользовательский бренд «Ось коммуникации» не меняет `kniterp-device-proof-v1`.

### Нестабильный тест повреждения

Полный прогон сначала выявил падение теста quarantine: изменение последнего байта внешнего pre-key-конверта не гарантировало изменения шифрованного тела. Теперь тесты находят ciphertext body через API libsignal и меняют бит именно в нём. Реализация шифрования и production-код доставки не менялись. После исправления проходят и откат состояния, и доставка корректного соседнего сообщения.

## Не выполнено и не готово

На этой версии не запускались Android instrumentation/Keystore на устройстве, живой HTTP-вход, серверные .NET/PostgreSQL тесты, закрытый HTTPS-стенд, реальные SMS, нагрузка и два физических телефона. Результаты Claude по HTTP/PostgreSQL остаются отдельно отмеченными авторскими результатами, а не независимым повтором этой проверки.

Экраны SMS/PIN, управление новыми активациями/профилями, единственный application-scope UserSession, восстановление UI и подключение пользовательского режима к NetworkModel ещё не реализованы. Операторский режим 0.2 остаётся отдельным. Контракт `/integrations/os/*` — проект, маршруты и служебная авторизация не реализованы. Сборка с новым брендом не означает завершение этапа 1.
