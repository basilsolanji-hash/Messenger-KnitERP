## Подтверждено без замечаний

- **Подмена устройства без подтверждения невозможна.** `acceptChange` заново вычисляет код из того bundle, который реально закрепляется, и сравнивает его в постоянном времени с кодом, показанным пользователю. При несовпадении бросается `IdentityChanged`, и вся транзакция откатывается: identity, сессии, `peer`, перешифрование. Тест сверяет набор ключей vault до и после. `receive()` по-прежнему отклоняет сообщения с нового устройства (`checkPeer` → `DeviceChanged`) и не подтверждает их, поэтому после принятия они приходят ровно один раз.
- **Между предпросмотром и подтверждением подменить bundle нельзя.** Используется тот же claim id. Сервер возвращает сохранённый `ResponseJson` или, если активное устройство сменилось, `CLAIM_CONFLICT`. Устаревшее устройство так не подтвердить. Другой bundle с другой identity отсекает сверка кода.
- `acceptChange` выполняет `deleteAllSessions`, перезапись identity, `SessionBuilder` и перешифрование в одной транзакции vault. Новые id не появляются, история не дублируется. `content.recipient` обновляется, и получатель проверяет его.
- Одновременная инициация сессии обеими сторонами (prekey-сообщения навстречу) сходится через предыдущие состояния сессии libsignal. Это проверено в JVM-тесте и `LiveTransferTest`, в обе стороны.
- Отказ `409 RECIPIENT_DEVICE_CHANGED` на сервере ничего не сохраняет: проверка стоит до `Envelopes.Add`, транзакция не фиксируется.
- `PeerChange` содержит только id и код безопасности. Новых логов с текстом нет.
- **Панель оператора.** CSP `default-src 'none'; script-src 'self'; frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff`, `no-referrer`, `no-store`. Страница без данных и без ключа. Весь вывод через `textContent`, `innerHTML` нет. Ключ хранится только в памяти страницы и передаётся заголовком, cookie нет (`credentials: 'omit'`), поэтому CSRF с чужого сайта невозможен: нестандартный заголовок требует CORS, а CORS не настроен. Ключ сравнивается в постоянном времени по SHA-256. В ответах нет токенов, кодов и номеров, это проверено тестом. Журнал `Operator action` без секретов. Nginx (`prepare-closed-https.py:195`) пускает `/api/v1/dev/*`, включая `panel.js`, только с операторских адресов.
- **`TakeDaily`.** Счётчик меняется атомарным `INSERT … ON CONFLICT DO UPDATE … WHERE Count+1 <= limit` в той же транзакции EF, что и claim. Отказы `429` и `PREKEYS_EXHAUSTED` откатывают счётчик. Ключ `claims-account:<id>:86400:<начало суток>` общий для всех экземпляров. Повтор с тем же claim id в лимит не засчитывается (тест подтверждает: 2 prekey израсходованы, 6 свободны). Просроченные окна чистит `AuthService.Cleanup`.
- **Тексты.** Во всех 4 языках по 128 ключей, наборы одинаковые, плейсхолдеры `%1$d` совпадают. В uz используются `‘`/`’`, неэкранированных `'` нет. Термины внутри каждого языка единые: «Код безопасности» / «Код бяспекі» / «Қауіпсіздік коды» / «Xavfsizlik kodi», везде «60 цифр». Смысл новых ключей совпадает с поведением, кроме находок 9 и 11.
- **Кнопки.** Все новые кнопки имеют обработчик и `enabled = enabled`. Повторное нажатие отбрасывается в `operation()` (`if (busy) return null`). `acceptPeerChange` требует `changed` и совпадения собеседника. Блокировка проходит только через диалог подтверждения. Локальная метка ставится только после ответа сервера, тест есть. Кнопка «Войти заново» скрыта при `auth_err_network`. ID аккаунта можно выделить (`SelectionContainer`).
