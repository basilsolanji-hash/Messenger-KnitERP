# Модель угроз для этапа 0

## Активы

Приватные ключи будущего клиента, непрочитанные конверты, публичные ключевые пакеты, сеансы устройств и метаданные маршрутизации. Приватные ключи Signal не должны появляться на сервере ни в одной последующей поставке.

## Границы доверия

Клиент отвечает за шифрование, проверку подписи key bundle и identity key, сохранение ratchet и outbox в одной локальной транзакции. Сервер принимает только непрозрачные конверты и минимальные маршрутизирующие поля. Поле с названием ciphertext нельзя считать доказательством корректного шифрования.

Сервер видит учетные записи, устройства, отправителей и получателей, время, длину передачи и состояние очереди. Этот этап не скрывает метаданные.

## Основные проверки

- Нельзя читать чужой inbox или подтверждать его сообщения.
- Старое устройство не проходит авторизацию после отзыва.
- Повторный запрос с тем же идентификатором не создает дубликат; измененное тело вызывает конфликт.
- ECC и PQ prekeys выдаются в одной транзакции; повтор claim возвращает прежний набор.
- Повтор upload не делает использованный prekey вновь доступным.
- SignalR и push не заменяют постоянную очередь.
- Подтверждение сервера отправляется после COMMIT.

## Ограничения прототипа

Тестовый provisioning token дает административное право создавать синтетические аккаунты и заменять устройства. Он действует только в локальном Development-стенде. Рабочая регистрация должна заменить этот путь целиком; перенос этого токена в публичный продукт запрещен архитектурой этапа.

В этом этапе нет защиты данных на устройстве, проверки подмены identity key и полноценной регистрации. Поэтому публичный запуск заблокирован в коде.
