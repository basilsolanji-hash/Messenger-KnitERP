# Messenger KnitERP

Первая серверная основа защищенного мессенджера под брендом **knitERP**.

**Статус: этап 0, прототип для разработки. Готового Android-приложения и подтвержденного сквозного шифрования всей системы пока нет. На Beget проект не развернут.**

## Что реализовано

- ASP.NET Core 10 и PostgreSQL, схема EF Core и начальная миграция.
- Тестовые учетные записи, access JWT на 15 минут, проверка действующего устройства и его generation.
- Публикация публичных prekeys и атомарная идемпотентная выдача пары ECC/PQ ключей. Проверка криптографических подписей должна выполняться клиентом через libsignal; сервер проверяет структуру и размеры.
- Постоянная очередь непрозрачных конвертов, дедупликация повторной отправки и отклонение конфликтующих повторов.
- Inbox с курсором, ACK после сохранения клиентом, очистка шифротекста после ACK и срока хранения.
- События SignalR через постоянный outbox. В hub не передаются тексты сообщений.
- Серверная блокировка новых отправок и смена тестового устройства с отзывом прежнего.
- Ограничения объема очереди, размера конверта и частоты запросов.

Сервер не умеет шифровать или расшифровывать сообщения. Прием поля `ciphertext` сам по себе не доказывает E2EE: это предстоит проверить с двумя настоящими клиентами.

## Запуск локального стенда

Нужны Docker с Compose и Python 3. Из корня проекта:

```bash
python3 scripts/init-dev.py
docker compose up --build -d
curl http://127.0.0.1:5080/health/live
curl http://127.0.0.1:5080/health/ready
```

`init-dev.py` создает случайные секреты в исключенном из git файле `.env` и не перезаписывает существующий файл. API опубликован только на `127.0.0.1:5080`, база не опубликована. Это локальный HTTP-стенд: не открывайте порт наружу и не используйте реальные персональные данные.

```bash
docker compose logs --tail=50 api
docker compose down
```

Обычный `down` сохраняет данные. Удаление volumes отдельно не входит в инструкцию запуска.

## Тестовые аккаунты

`POST /api/v1/dev/accounts` требует заголовок `X-Dev-Provisioning-Token` со значением локального `Dev__ProvisioningKey`. Тело содержит `displayName`, случайный `deviceId`, `registrationId` в диапазоне 1–16383 и `identityKey` как base64 от 33 байтов. Это заглушка процедуры регистрации для синтетических тестов, а не SMS-вход.

Остальные API требуют `Authorization: Bearer <accessToken>`. OpenAPI доступен по `/openapi/v1.json` с таким же заголовком. Публичные ключи и сообщения передаются как base64-строки; приватных ключей в API нет.

Запуск вне `Development` намеренно завершается ошибкой. Этот предохранитель нельзя убирать до внедрения SMS, PIN, refresh rotation, подтверждения владения устройством и проверки безопасности.

## Сборка и проверки

Нужен SDK из `global.json`:

```bash
dotnet restore server/Messenger.Tests --locked-mode
dotnet build server/Messenger.Api -c Release --no-restore
dotnet test server/Messenger.Tests --no-restore --filter Category=Unit
```

Интеграционные тесты требуют отдельную PostgreSQL, где разрешено создавать временные схемы. Задайте `TEST_DATABASE` стандартной строкой подключения Npgsql, затем:

```bash
dotnet test server/Messenger.Tests --filter Category=PostgreSQL
```

Тесты создают случайную схему `test_<uuid>` и удаляют только ее. В отсутствие `TEST_DATABASE` интеграционные тесты завершаются ошибкой, а не притворяются пройденными. Workflow GitHub Actions запускает весь набор на отдельной PostgreSQL 18 после появления кода в репозитории.

## Следующая поставка

1. Kotlin-модуль с настоящим libsignal, PQXDH и транзакционным хранилищем состояния.
2. Android Compose, Room и SQLCipher, ключ базы под Android Keystore, существующий логотип knitERP.
3. Первая переписка двух клиентов, включая офлайн-доставку и сбои между сохранением ратчета и ACK.
4. Полная регистрация SMS, PIN и recovery code, refresh tokens, подписанные device challenges.
